# Question recording

The browser still computes all answers. At the end of each attempt it sends `POST /api/questions` with a random UUID, election ID, question (max 600 characters) and outcome: `answered`, `unsupported`, `empty`, `failed` or `cancelled`. The server adds an ISO receipt timestamp, derived `answered` boolean and `source: browser`. Outcome is client-reported, not independently verified correctness. No IP, cookie, user ID, fingerprint or answer payload is collected; free-text questions can still contain voluntarily entered personal data. The page says that questions are saved.

A dedicated 128MB/5-second Lambda writes to a private PAY_PER_REQUEST DynamoDB table. The UUID is its primary key. A conditional PutItem preserves the first record and deduplicates retries after a lost HTTP response. The `by-outcome-time` GSI uses outcome as partition key and receivedAt as sort key, enabling time-range queries for a selected outcome without a scan. Use descending sort for newest first and paginate using LastEvaluatedKey. GSI results are eventually consistent; different outcomes require separate queries. Election filtering can be applied after each outcome query.

The writer has only PutItem on its own table and writes generic failure diagnostics to a dedicated CloudWatch log group with 14-day retention. The public API cannot read, list or update records. Existing account-authorized DynamoDB tools can inspect records or extend a resolution workflow later. No public dashboard or mark-as-resolved API is added here. Table data is encrypted, retained on stack deletion/replacement and has no automatic TTL. Each environment gets its own generated table; `QuestionLogTableName` is exposed in the backend stack outputs.

The HTTP API and CloudFront origin are reused. `/api/*` routes to the HTTP API, not the static client; logs return no-store. The endpoint is throttled to 2 requests/second, burst 4, with Lambda concurrency 2 and no provisioned concurrency/always-on instance. These limits reduce load but do not guarantee a spend cap. Public feedback can be spammed and client-reported status is not an audited success metric.

Answer rendering never waits for recording. The client retries transient failures once with the same UUID and uses a 4-second per-attempt timeout and keepalive. If recording still fails, a quiet status message reports it while preserving the answer. Cancellation after input edits or navigation is reported as cancelled. Browser crashes, closure and offline clients can still lose records; keepalive is best-effort. Do not infer success from missing attempts.

Deployment creates the table/index/function/route via t01, updates CloudFront via t00, and explicitly refreshes the new Lambda code using `QuestionLogFunctionName` from the stack outputs. CloudFormation alone cannot detect replacement code at the unchanged dist.zip key. No production deployment is part of this PR.
